Message Authentication Code (MAC): a keyed algorithm that produces an authentication tag from a message. A secure scheme makes a valid tag for a fresh, unauthorized message hard to forge without the key.

A matching tag supports integrity and data-origin authentication relative to the shared-key holders. It does not identify which key holder made the tag. Bob knows K too, so Bob can create the same tags.

First, learn the vocabulary

M · message
The exact bytes being authenticated. It can be a sentence, a file, or a structured request.
K · secret key
Secret bytes shared by the sender and verifier. They are an input to the algorithm, not the transmitted tag.
T · tag
The fixed-size authentication result. “MAC” can mean the construction or this output, depending on context.
H · hash function
A deterministic function that maps bytes of any supported length to a fixed-size digest. An ordinary hash has no secret key.
EK · block encryption
A keyed transformation of one fixed-width block. In our CMAC example it is AES-128 encryption of a 16-byte block.
Verification
Recompute the expected tag from the received message and secret key, then compare with the received tag.

Read the symbols, not just the formula

⊕

XOR: combine equal-length bit strings, bit by bit. Equal bits give 0; different bits give 1. Example: 1010 ⊕ 1100 = 0110.

||

Concatenate: append one byte string after another. 41 42 || 43 = 41 42 43. It increases length; XOR does not.

0ⁿ

n zero bits: 0¹²⁸ is a 16-byte all-zero block.

hex

Hexadecimal: two hex digits describe one byte. 80 is the byte 10000000. A 32-byte tag is shown as 64 hex digits.

1 byte = 8 bits · 16 bytes = 128 bits · 64 bytes = 512 bits

Try the receiver’s decision

This demonstration authenticates a message once using HMAC-SHA-256 and the public teaching key class-demo-key. Changing the received message does not silently replace its original tag.

The key above is intentionally public for learning. In a real protocol K must be secret, verification uses a constant-time tag comparison, and the application authenticates every field that matters.

Why a bare hash is insufficient

M + H(M)A public message and public digest
→
Eve changes M to M′She can also calculate H(M′)
→
M′ + H(M′)Both can be replaced

A hash is useful if its reference value is independently trusted. Sending an unkeyed digest alongside a replaceable message does not authenticate the sender. A MAC adds a secret to the calculation.

What the tag does not provide

  • Confidentiality: M remains readable unless separately encrypted.
  • Non-repudiation: both Alice and Bob know K, so either can make T. A shared-key MAC is not a digital signature.
  • Freshness: a valid old packet still has a valid tag. Authenticate a sequence number or nonce and check it against receiver state to reject replay.
  • Protection after key compromise: someone with K can make new valid tags.

For replay, an authenticated sequence number is only useful if Bob also rejects numbers already used. Including a field and checking a field are two separate requirements.

HASH-BASED MESSAGE AUTHENTICATION CODE

HMAC: put one hash inside another.

Use the same hash algorithm for both passes. First hash the message after an inner key-derived prefix. Then hash that digest after a different outer key-derived prefix. The outer digest is the tag.

OUTER HASH · produces the tag
K₀ ⊕ opad||
INNER HASH · produces digest I
K₀ ⊕ ipad||Message M

H(inner prefix || M) → I

H(outer prefix || I) → T

I = H((K₀ ⊕ ipad) || M)
T = H((K₀ ⊕ opad) || I)

Read from the innermost parentheses outward. I is a digest, not ciphertext. The outer pass receives I's raw bytes, not the original M and not the characters of I's hex display.

Construction formula: RFC 2104, section 2. Trace examples: RFC 4231.

Three lengths that are easy to mix up

SHA-256 input block B = 64 bytes

The hash processes input internally in 64-byte blocks. Messages can be longer than one block.

SHA-256 output L = 32 bytes

Every full digest is 32 bytes, irrespective of message length.

HMAC key K = variable length

Normalize it to K₀ of exactly B bytes. A production key should have suitable random entropy; this page's short text keys are teaching examples.

What are ipad and opad?

ipad: the byte 36 repeated B times. opad: the byte 5c repeated B times. These are public constants. XORing each with K₀ makes two distinct, secret-derived prefixes.

K₀Same normalized secret key
→
Inner: K₀ ⊕ 36…3664-byte prefixOuter: K₀ ⊕ 5c…5cDifferent 64-byte prefix

“Pad” here names the public XOR patterns. It does not mean ordinary message padding. SHA-256 still applies its own internal length padding whenever H is called.

The two-layer keyed construction avoids the simple secret-prefix-hash design. With a Merkle–Damgård hash such as SHA-256, H(K || M) can expose a length-extension path; it is not HMAC.

CIPHER-BASED MESSAGE AUTHENTICATION CODE

CMAC: chain blocks, then mark the ending.

CMAC uses a block cipher as its building block. Here, AES-128 accepts one 16-byte block and a 16-byte secret key. Break M into blocks, combine each with the preceding state using XOR, and encrypt. The final block receives an extra key-derived mask.

X₀ = 0¹²⁸Fixed initial zero state
→
⊕ M₁ → AESKProduces X₁
→
⊕ M₂ → AESKProduces X₂ · keep chaining
→
⊕ modified final block → AESKLast output is tag T

Only include the ordinary blocks that actually exist. For a one-block message, go directly from X₀ to the modified final block. A zero-length message still has one padded final block.

Intermediate values X₁, X₂, … are chaining states. You do not send them as ciphertext blocks. CMAC outputs the final tag, while the original message may still be sent openly.

Authentication mode: NIST SP 800-38B. AES-128 examples and subkey formula: RFC 4493.

The final block has two paths

The question is whether the original message has a nonzero length that is exactly divisible by 16 bytes. Check this before adding padding.

YES · full final block

Use K₁. Add no padding.

Mₙ · 16 bytes
→
Mₙ* = Mₙ ⊕ K₁

Examples: 16, 32, 48, 64 bytes.

NO · short final block or empty message

Pad, then use K₂.

Remaining bytes0 to 15 bytes
→
Append 1 then zero bitsFor byte input: append 80, then 00…
→
Mₙ* = padded block ⊕ K₂

Examples: 0, 1, 15, 17, 40 bytes.

Both paths produce one 16-byte effective final block. The masks distinguish complete and padded endings; padding alone is not CMAC's final-block treatment.

Where do K₁ and K₂ come from?

They are derived from the original AES key K, rather than separately exchanged. They are not AES round keys.

0¹²⁸ · all-zero block
→
AESKOriginal K is the AES key
→
LSubkey seed · 16 bytes
L→ double →K₁→ double →K₂

L = AES_K(0¹²⁸)
K₁ = dbl(L)
K₂ = dbl(K₁)

At every chaining step AES still uses K. K₁ or K₂ is XORed into the final message block; it does not replace the AES key.

“Double” means a bit operation

Treat the whole 16-byte string as one 128-bit value, most significant bit first. Shift left one bit across byte boundaries, discarding the bit shifted out.

Old first bit = 0

dbl(X) = X << 1

Old first bit = 1

dbl(X) = (X << 1) ⊕ Rb

Rb = 00 00 … 00 87 is 16 bytes. Its last byte is 87; the other 15 are zero. It is a fixed field-reduction constant, not a key or an IV.

This is multiplication by x in GF(2¹²⁸), represented as a shift with reduction using x¹²⁸ + x⁷ + x² + x + 1. You can calculate the shift/XOR without deriving the field theory. It differs from AES's byte field GF(2⁸).

Use the original high bit to decide whether to XOR Rb. Test it before shifting.

Why not use ordinary CBC-MAC for any length?

The basic zero-initialized construction Xᵢ = E_K(Xᵢ₋₁ ⊕ Mᵢ) can be secure for an agreed fixed message length. Extending it naively to variable-length messages permits algebraic forgeries.

Known one-block message MKnown tag T = E_K(M)
→
Construct M || (M ⊕ T)Different, two-block message
→
Second state = E_K(T ⊕ M ⊕ T)= E_K(M) = T

The same known tag authenticates a new message in that naive scheme. CMAC's end masks change this structure and give a construction for variable message lengths. “Use AES” alone does not make an authentication design safe.

Same job. Different machinery.

Both algorithms take a secret key and message and return a tag. Neither is a message-encryption scheme.

HMAC-SHA-256

Hash-based

Public patterns: 36…36 and 5c…5c.

AES-128-CMAC

Cipher-based

Derive K₁, K₂ from AES_K(0)↓Split M into 16-byte blocks↓Final block: K₁, or pad + K₂↓Start X₀ = 0; XOR and encrypt↓ last AES output16-byte tag T

These widths belong to the concrete variants on this page. HMAC with SHA-512 uses other hash widths; AES-CMAC can use other AES key sizes while retaining 16-byte blocks. A shorter tag must follow the chosen protocol's truncation rule.

Six confusions, resolved visually

Hash ≠ MAC

H(M) has no secret.
MAC(K,M) needs K.

Tag ≠ ciphertext

M → T makes a check.
It does not hide or recover M.

XOR ≠ append

16B ⊕ 16B → 16B
16B || 16B → 32B

HMAC K₀ ≠ tag

K₀: 64B is the padded key.
T: 32B is the output.

CMAC K₁/K₂ ≠ AES keys

They mask the ending.
AES uses original K every time.

Validity ≠ freshness

A replay preserves M and T.
MAC alone will accept it again.

Three different meanings of “padding”

HMAC key normalization

Pad a short or hashed key with zero bytes to the hash block width. This creates K₀.

K′ || 00…00 → K₀
Hash's internal padding

SHA-256 appends a one bit, zeros, and a length field inside each H call. The hash function handles it.

input || 80… || bit length
CMAC partial-message padding

Append one bit, then zeros, to fill a partial or empty final block. Then XOR K₂.

(remaining || 80…00) ⊕ K₂

CMAC does not append an extra padding block when the original message already ends in a full, nonempty block. HMAC's key padding does not replace SHA-256's internal padding.

Exam-ready answers

Define a MAC in two sentences.

A Message Authentication Code is a symmetric keyed function that maps a message to an authentication tag. The receiver recomputes the tag using the shared secret and compares it with the received tag to check integrity and data-origin authentication.

Explain HMAC with its formula and stages.

Normalize K to the hash block width to obtain K₀, hashing K first if it is too long and zero-padding if required. Compute I = H((K₀ ⊕ ipad) || M), then T = H((K₀ ⊕ opad) || I). ipad and opad are the public repeated bytes 36 and 5c. The final outer digest is the MAC tag.

Explain CMAC with the two last-block cases.

Derive L = E_K(0ᵇ), K₁ = dbl(L), and K₂ = dbl(K₁). If the original message ends in a full nonempty block, XOR that block with K₁. Otherwise append a one bit and zeros to fill the final block, then XOR K₂. Starting from X₀ = 0ᵇ, encrypt each block XORed with the preceding state; use the modified final block at the last step. The last state is the tag.

Why does a MAC not provide non-repudiation?

The verifier possesses the same secret key and can generate valid tags. A third party cannot distinguish which shared-key holder generated a given MAC.

Explain the naive CBC-MAC variable-length problem.

For a one-block message M with tag T = E_K(M), the two-block message M || (M ⊕ T) also has tag T: its second state is E_K(T ⊕ M ⊕ T) = E_K(M). CMAC adds keyed final-block treatment rather than using this naive construction for arbitrary lengths.

Quick checks · answer before revealing

HMAC-SHA-256 with a 65-byte key: what happens first?

Hash the 65-byte key to 32 bytes, then append 32 zero bytes to make the 64-byte K₀. A 64-byte key itself is not hashed in normalization.

Is HMAC's outer input 64-byte prefix + original message?

No. It is 64-byte outer prefix + 32 raw bytes of inner SHA-256 digest, so 96 bytes before SHA's internal padding.

AES-CMAC of a 32-byte message: K₁ or K₂?

K₁. There are two full blocks. Modify only block 2; no padding is added.

AES-CMAC of a 17-byte message: describe every block.

Block 1 contains 16 message bytes. Block 2 starts with the remaining byte, then 80 and fourteen 00 bytes; XOR K₂ into that padded block. Both chaining encryptions use the original key K.

AES-CMAC of an empty message: are there zero AES operations?

No. The message has one effective padded final block: 80 followed by fifteen 00 bytes, XORed with K₂ and processed once. Subkey generation also includes AES_K(0).

Does the receiver decrypt a CMAC tag?

No. The receiver computes CMAC on the received message with K and compares tags. It need not use AES decryption.

What if an attacker resends a valid old M and T?

The tag remains valid. Freshness requires authenticated protocol data, such as a sequence number, and a receiver check for reuse.

Is a short final block padded with only zeros?

No. CMAC appends one bit and then zero bits. For byte-aligned input this is byte 80 followed by zero bytes.

  • Define M, K, T, H, E_K, XOR, and concatenation.
  • Draw HMAC's inner digest flowing into its outer hash.
  • Normalize 4-, 64-, and 65-byte SHA-256 keys.
  • Select CMAC's final-block path for 0, 15, 16, 17, and 32 bytes.
  • Describe CMAC subkey derivation and the original-high-bit test.
  • Calculate a byte XOR and interpret the actual chain values.
  • State integrity/authentication and the limits: secrecy, non-repudiation, replay.
